# BUG-017: Tipo de Conteo "Inicial" Debe Determinarse Automáticamente

**Type**: Spec gap (requirement missing from user story, architectural decision needed)
**Severity**: High
**Feature**: 009-inventario-conteo
**Reported**: 2026-07-19
**Status**: ✅ Patched (2026-07-19)

---

## Descripción del Problema

Al iniciar un conteo, el campo "Tipo de conteo" actualmente presenta la opción "Inicial" como selectable por el usuario junto a `diario`, `semanal` y `mensual`.

**Problema Identificado**: Esta selección manual de "Inicial" es **incorrecta desde la perspectiva operativa**.

### Comportamiento Actual (❌ Incorrecto)

```text
POST /api/v1/inventarios
{
  "tienda_id": 1,
  "tipo": "inicial",        ← Usuario elige manualmente
  "horario": null           ← N/A para tipo inicial
}

↓ Response: 201 Created
{
  "id": 123,
  "tipo": "inicial",
  "estado": "en_progreso"
}
```

### Comportamiento Requerido (✅ Correcto)

El tipo de conteo **debe determinarse internamente** por el sistema basándose en el historial de inventarios previos:

```text
POST /api/v1/inventarios
{
  "tienda_id": 1,
  "tipo": "diario",         ← Usuario elige (diario, semanal, mensual)
  "horario": "apertura"     ← Según hora
}

↓ Service Logic:
  1. Consultar: ¿Existe algún inventario COMPLETADO anterior en esta tienda?
     - SELECT COUNT(*) FROM inventarios
       WHERE tienda_id = ? AND estado = 'completado'

  2. Si NO existe (COUNT = 0):
     - Sistema determina automáticamente: tipo_real = "inicial"
     - Usuario NO ve ni elige "inicial"

  3. Si SÍ existe (COUNT ≥ 1):
     - Sistema determina automáticamente: tipo_real = "diario" (o semanal/mensual elegido)
     - Usuario NO ve "inicial"

↓ Response: 201 Created
{
  "id": 123,
  "tipo": "inicial",        ← Determinado por sistema, no elegido por usuario
  "estado": "en_progreso"
}
```

## Análisis de Requisitos Afectados

### RF-INV-01.3 (CONFLICTO IDENTIFICADO)

**Texto actual**:
> El usuario puede cambiar el tipo manualmente a `diario`, `semanal`, `mensual` o `inicial` sin restricción de horario.

**Problema**: Permite selección manual de "inicial", pero el nuevo requisito dice que "inicial" debe ser **determinación automática**.

**Acción requerida**: Actualizar RF-INV-01.3 para remover `inicial` de las opciones manuales.

### RF-INV-01.5 (CLARIFICACIÓN NECESARIA)

**Texto actual**:
> El tipo `inicial` se usa exclusivamente para la carga inaugural de stock de la tienda. No requiere inventario de referencia previo.

**Clarificación**: Esto es **correcto**, pero falta especificar QUE EL SISTEMA DEBE DETERMINAR CUÁNDO APLICARLO.

**Propuesta de reemplazo**:
> El tipo `inicial` es determinado automáticamente por el sistema cuando realiza el primer conteo de una tienda (sin historial de inventarios completados). El usuario NO puede seleccionar "inicial" manualmente; el sistema lo determina consultando si existe inventario completado previo en la tienda. Si existe, el tipo es la categoría elegida por el usuario (diario/semanal/mensual). Si no existe, el tipo es "inicial" independientemente de lo que el usuario haya seleccionado.

### Historia de Usuario 1, Escenario 4 (REQUIERE AJUSTE)

**Texto actual**:
> **Dado** que es el primer conteo de la tienda (sin historial previo),
> **Cuando** el líder inicia el inventario de tipo `inicial`,
> **Entonces** el sistema presenta todos los items activos...

**Cambio requerido**:
> **Dado** que es el primer conteo de la tienda (sin historial de inventarios completados previo),
> **Cuando** el líder inicia un inventario (y selecciona cualquier tipo diario/semanal/mensual),
> **Entonces** el sistema detecta automáticamente que NO existe historial previo y determina que el tipo es `inicial`, presentando todos los items activos...

## Impacto en Capas

### Backend (loopi-api-v2)

**Afectado**: `internal/inventarios/service.go` — método `Iniciar()`

```go
// ANTES (actual):
func (s *Service) Iniciar(ctx context.Context, req *CreateInventarioReq, ...) (*InventarioResp, error) {
    // ... validaciones ...

    // El tipo viene directamente del request del usuario
    inv := &Inventario{
        Tipo: req.Tipo,  // ← Si usuario envía "inicial", se acepta
        ...
    }
    // ...
}

// DESPUÉS (requerido):
func (s *Service) Iniciar(ctx context.Context, req *CreateInventarioReq, ...) (*InventarioResp, error) {
    // ... validaciones ...

    // 1. Determinar si existe inventario completado previo
    existeHistorial, err := s.repo.ExisteInventarioCompletado(ctx, req.TiendaID)
    if err != nil {
        return nil, err
    }

    // 2. Calcular tipo real
    tipoReal := req.Tipo  // Tipo elegido por usuario (diario/semanal/mensual)
    if !existeHistorial {
        tipoReal = "inicial"  // Sistema sobrescribe a inicial
    }

    // 3. Validar que usuario no seleccionó "inicial" manualmente
    if req.Tipo == "inicial" {
        return nil, NewError("tipo_inicial_no_permitido",
            "El tipo 'inicial' es determinado automáticamente por el sistema")
    }

    inv := &Inventario{
        Tipo: tipoReal,  // ← Tipo determinado por sistema
        ...
    }
    // ...
}
```

**Nuevas funciones Repository requeridas**:

```go
// Verifica si existe algún inventario completado en una tienda
func (r *Repository) ExisteInventarioCompletado(ctx context.Context, tiendaID int64) (bool, error)

// Query sugerida:
// SELECT EXISTS(
//   SELECT 1 FROM inventarios
//   WHERE tienda_id = ? AND estado = 'completado'
//   LIMIT 1
// )
```

**Error code nuevo**:

- Código: `tipo_inicial_no_permitido`
- Status HTTP: 400 Bad Request
- Mensaje: "El tipo 'inicial' no puede ser seleccionado manualmente. El sistema lo determina automáticamente en el primer conteo de la tienda."

### Frontend (loopi-web-v2)

**Afectado**: `src/app/inventario/inventario-conteo.component.ts` — método `onSelectTipo()` o equivalent

## Casos de Uso Afectados

### Caso 1: Primera tienda (Primer conteo de la tienda)

```text
Historial previo: NINGUNO (primera vez que se cuenta en esta tienda)

Usuario elige: tipo = "diario", horario = "apertura"
Sistema determina: tipo_real = "inicial" (NO existe historial completado)
Resultado: Se crea como tipo "inicial", se presentan TODOS los items (RF-INV-01.6)
```

### Caso 2: Tienda con historial previo (Conteo posterior)

```text
Historial previo: SÍ (existe inventario completado de fecha anterior)

Usuario elige: tipo = "diario", horario = "apertura"
Sistema determina: tipo_real = "diario" (SÍ existe historial completado)
Resultado: Se crea como tipo "diario", se presentan solo items con frecuencia diaria
```

### Caso 3: Usuario intenta seleccionar "Inicial" manualmente (BLOQUEADO)

```text
Usuario intenta enviar: POST /inventarios { tipo: "inicial", ... }
Backend retorna: 400 Bad Request
Código de error: tipo_inicial_no_permitido
Mensaje: "El tipo 'inicial' no puede ser seleccionado manualmente..."
```

## Root Cause Analysis

**Por qué ocurrió este gap**:

1. **Especificación Original (RF-INV-01.3)** permitía selección manual de "inicial"
2. **Diseño permitía** al usuario elegir cualquier tipo, incluyendo inicial
3. **Falta de claridad operativa**: No se especificó que "inicial" debe ser **determinación automática** basada en historial
4. **Implementación Frontend** expuso opción "Inicial" en dropdown sin validar si es primer conteo
5. **Validación Backend** aceptaba tipo="inicial" sin verificar si debe serlo

## Consideraciones Operativas

### Beneficio del Cambio

- **Claridad operativa**: Usuario no se confunde con opción "Inicial"
- **Integridad de datos**: Sistema garantiza que "inicial" solo ocurre en primer conteo
- **Prevención de errores**: Elimina posibilidad de usuario marcar manualmente un conteo posterior como "inicial"
- **Auditoría**: Registro claro de cuándo se realizó el primer conteo (tipo="inicial" siempre es el primero)

### Impacto en Usuarios

- **Positivo**: Formulario más simple (3 opciones en lugar de 4)
- **Positivo**: Lógica "mágica" simplifica flujo operativo
- **Neutro**: Primera tienda sigue siendo fácil de contar (usuario elige cualquier tipo, sistema aplica "inicial")
- **Neutro**: Conteos posteriores funcionan igual
