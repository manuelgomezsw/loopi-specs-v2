# BUG-021: Validación de Horario Incompleta en Cambio de Tipo + Determinación Automática

**Type**: Implementation drift (Frontend no sincroniza con lógica de Backend)
**Severity**: High
**Feature**: 009-inventario-conteo
**Reported**: 2026-07-19

---

## Descripción

Cuando el usuario intenta iniciar un conteo **semanal o mensual**, el sistema rechaza la solicitud con error:

```text
horario_not_allowed: horario no debe ser especificado para conteos semanales, mensuales o iniciales
```

El problema es que el campo `horario` en el formulario frontend **retiene su valor anterior** cuando el usuario cambia manualmente el tipo de `diario` a `semanal`/`mensual`.

### Flujo que reproduc el bug

1. Página carga → `getSugerencia()` retorna tipo='diario', horario='apertura' (o mediodía/cierre según la hora)
2. Formulario se rellena: `tipo='diario'`, `horario='apertura'`
3. Usuario cambia manualmente el tipo a **'semanal'** (dropdown o select)
4. El validador del campo `horario` se limpia (línea 75 del component.ts)
5. **PERO el valor del campo horario sigue siendo 'apertura'**
6. Usuario hace click en "Iniciar conteo"
7. Se envía al backend: `{ tipo: 'semanal', horario: 'apertura' }`
8. Backend rechaza (línea 606 de service.go): "horario_not_allowed"

## Root Cause Analysis

**Causa raíz**: Lógica incompleta de reacción a cambios en el formulario.

En `inventario-conteo.component.ts` líneas 68-78:

```typescript
this.formulario.get('tipo')?.valueChanges
  .pipe(takeUntil(this.destroy$))
  .subscribe(tipo => {
    const horarioControl = this.formulario.get('horario');
    if (tipo === 'diario') {
      horarioControl?.setValidators(Validators.required);
    } else {
      horarioControl?.clearValidators();  // ⚠️ Solo limpia validadores, NO el valor
    }
    horarioControl?.updateValueAndValidity();
  });
```

**El problema específico**:

- Cuando tipo cambia a 'semanal'/'mensual'/'inicial', se llama `clearValidators()`
- Esto **LIMPIA los validadores** pero **NO limpia el VALUE** del control
- El campo horario retiene su valor anterior (ej: 'apertura' de cuando era 'diario')
- Al enviar, se envía `{ tipo: 'semanal', horario: 'apertura' }`
- Backend correctamente rechaza esto porque horario no debe estar presente

**Validación backend es CORRECTA**:
Línea 606 de `service.go`:

```go
if horario != nil && (tipo == TipoSemanal || tipo == TipoMensual || tipo == TipoInicial) {
    return NewError("horario_not_allowed", "...")
}
```

Esta lógica es correcta per RF-INV-01.2 y RF-INV-01.3. El bug está 100% en frontend.

## Solución Recomendada

**Opción 1 (Recomendada)**: Limpiar valor cuando tipo cambia a semanal/mensual

En `inventario-conteo.component.ts` línea 75, cambiar:

```typescript
} else {
  horarioControl?.clearValidators();
  horarioControl?.setValue(null); // ← AGREGAR esta línea
}
```

**Opción 2**: Usar `formValue.horario || undefined` en línea 203 (YA ESTÁ IMPLEMENTADO)

En realidad, línea 203 ya tiene:

```typescript
horario: formValue.horario || undefined
```

Así que si se pasara `null`, debería funcionar. El problema es que se está pasando `'apertura'` en lugar de `null`.

**Opción 3**: Resetear todo el formulario cuando tipo cambia (menos invasivo)

```typescript
} else {
  horarioControl?.reset(null, { emitEvent: false }); // Reset sin emitir changeEvent
  horarioControl?.clearValidators();
}
```

## 🔴 SEGUNDA VARIANTE: Backend No Revalida Horario Tras Determinación Automática (BUG-021-B)

**Escenario**: Aunque el frontend envíe datos correctos, hay un gap lógico en el backend.

**Flujo problemático**:

1. User envía: `{ tipo: "diario", horario: "apertura" }` (válido para diario)
2. `ValidarTipo("diario")` — ✅ pasa (línea 92)
3. `ValidarHorario("apertura", "diario")` — ✅ pasa (diario requiere horario, línea 100)
4. Sistema verifica: NO existe historial previo en tienda
5. Línea 152: `tipoReal = TipoInicial` (se determina automáticamente como inicial)
6. Línea 168: Se crea inventario con:

   ```go
   Tipo:    TipoInicial    ← Determinado automáticamente
   Horario: "apertura"    ← ¡PERO ESTO VIOLA RF-INV-01.2!
   ```

**Por qué es problema**:

- RF-INV-01.2 y el algoritmo especificado en spec.md dicen que tipo "inicial" NO DEBE tener horario
- Solo tipo "diario" debe tener horario
- Backend pasa validación porque valida `(horario, req.Tipo)` ANTES de determinar el tipo real

**Causa raíz backend**:
Orden incorrecto de operaciones. Línea 100 valida horario contra `req.Tipo` (solicitado), no contra `tipoReal` (determinado).

Luego en líneas 149-152 se determina automáticamente `tipoReal`, pero la validación de horario ya pasó usando el tipo anterior.

**Solución backend recomendada**:
Revalidar horario DESPUÉS de determinar `tipoReal`:

```go
// Paso 1: Validar tipo solicitado
if err := s.ValidarTipo(req.Tipo); err != nil { ... }

// Paso 2: Query items ANTES de crear inventario
itemIDs, err := s.repo.GetItemsActivosPorTipo(ctx, req.TiendaID, req.Tipo); ...

// Paso 3: Determinar tipo real según historial
tipoReal := req.Tipo
if !existeHistorial {
    tipoReal = TipoInicial
}

// ⭐ NUEVO: Validar horario DESPUÉS de determinar tipoReal
if err := s.ValidarHorario(req.Horario, tipoReal); err != nil {
    return nil, err
}

// Paso 4: Crear inventario con tipoReal
inv := &Inventario{
    Tipo:    tipoReal,
    Horario: req.Horario,
    ...
}
```

O mejor aún: **Forzar horario a null cuando tipo es inicial**:

```go
inv := &Inventario{
    Tipo:    tipoReal,
    Horario: req.Horario,  // Será null si tipoReal es TipoInicial
    ...
}

// PERO agregar lógica: si tipoReal es TipoInicial, forzar Horario = null
if tipoReal == TipoInicial {
    inv.Horario = nil
}
```
