## Descripción del Bug

Actualmente el modelo de datos mantiene **dos campos redundantes** en `detalle_inventario`:

1. **valor_sugerido**: Snapshot inmutable del stock al inicio del conteo
2. **valor_esperado**: Stock proyectado al momento de POST /inventarios

**Problema identificado**:

En la práctica, ambos campos tienen el **mismo valor** al momento de crear el conteo:

- Ambos se inicializan con el stock snapshot calculado per RF-INV-02.2
- La diferencia se calcula contra `valor_esperado` (no contra `valor_sugerido`)
- El operador **no necesita ver** `valor_sugerido` en pantalla (solo ve "Esperado")
- El campo `valor_sugerido` solo sirve para auditoría histórica, pero genera confusión

**Impacto**:

- Confusión en frontend: ¿mostrar sugerido o esperado?
- Complejidad innecesaria en backend y BD
- Duplicación de almacenamiento
- Inconsistencia conceptual: spec define dos campos sin aclarar su propósito diferenciado

**Decisión**: Eliminar `valor_sugerido` completamente. El campo `valor_esperado` es suficiente y más claro semánticamente.

## Root Cause Analysis

1. **Diseño inicial**: Se incluyeron dos campos para "auditoría de sugerencia vs realidad"
2. **Realidad práctica**: Ambos valores son idénticos al inicio; `valor_esperado` es suficiente
3. **Evolución del spec**: La spec no aclaró propósito diferenciado → generó confusión implementativa

---

## Solución Recomendada

**Opción**: Eliminar completamente `valor_sugerido`

Mantener solo `valor_esperado` que:

- Se calcula per RF-INV-02.2 fórmula (stock_ref + compras - ventas - mermas)
- Es inmutable durante el conteo (no se permiten movimientos)
- Es el valor contra el que se calcula diferencia (per spec)
- Es suficiente para auditoría (snapshot de qué se esperaba)

**Beneficios**:

- ✅ Simplificar BD, backend, frontend
- ✅ Claridad semántica (un campo = un propósito)
- ✅ Reducir complejidad de DTOs
- ✅ Eliminar confusión operativa
